# SS-US-01: Login — What Claude Produced, and How

This document explains how **SS-US-01: Login (ADMIN, USER)** was taken through all 6 AIF-SDLC steps (Spec → Design → Quality → Implementation → Deployment → Verification), per [aif-sdlc.md](../aif-sdlc.md), in two halves:

- **What Claude produced** — every file created or modified at each step. For each file: what it is, why it was created, when it's used, and how it works.
- **How Claude produced it** — the input documents Claude read at each step and, for each, exactly what information it pulled out and which downstream artifact that information fed.

Deployment (Step 5) produced no new files — it only ran the existing test suites and started the dev servers, so it has no entry here.

### [backend/users/tests.py](../backend/users/tests.py)

| Aspect | Detail |
|---|---|
| What | The Django `APITestCase` suite for login — 6 tests (`test_tc01`..`test_tc09`), replacing an empty stub. |
| Why | Constitution.md's DOD-05 and "Integration Testing Over Mocking" principle require real API tests against a real (throwaway) test database — no mocking of models/querysets. |
| When | Run via `python manage.py test users` (or `python manage.py test` for the full suite) — during Implementation (T008), Deployment (regression check), and Verification (re-confirmed fresh). |
| How | Each test creates a real user with `User.objects.create_user` (hashed password; originally via the then-public registration endpoint, which UM-US-01 made ADMIN-only), then exercises the login endpoint and asserts the exact status code and response shape — e.g. `test_tc05` deactivates an account mid-test and confirms it gets the *same* generic 401 body as a wrong password, proving AC-02 and AC-03 are indistinguishable to the caller. |

### [frontend/src/app/login/page.tsx](../frontend/src/app/login/page.tsx)

| Aspect | Detail |
|---|---|
| What | The actual Login page — a Next.js/React client component at the `/login` route. |
| Why | It didn't exist at all before this US; SS-US-01 needs a real UI, not just a backend endpoint. |
| When | Every time a User opens `http://<host>:3000/login` — it's the literal feature being delivered. |
| How | A `"use client"` component with `useState` for `email`/`password`/`error`/`loading`. On submit: if either field is empty, shows `"Email and password are required."` without calling the API (EC-01); otherwise `fetch`es `POST ${apiOrigin}/api/v1/auth/login/` (native fetch, no HTTP client library, per constitution FE-08); on failure shows `"Invalid email or password."` (AC-02/AC-03); on success stores the `access`/`refresh` tokens in `localStorage` and redirects via `useRouter().push('/')` (AC-01). The submit button disables and shows "Logging in..." while the request is in flight (FE-06). |
