# SS-US-01: Login — What Claude Produced, and How

This document explains how **SS-US-01: Login (ADMIN, USER)** was taken through all 6 AIF-SDLC steps (Spec → Design → Quality → Implementation → Deployment → Verification), per [aif-sdlc.md](aif-sdlc.md), in two halves:

- **What Claude produced** — every file created or modified at each step. For each file: what it is, why it was created, when it's used, and how it works.
- **How Claude produced it** — the input documents Claude read at each step and, for each, exactly what information it pulled out and which downstream artifact that information fed.

Deployment (Step 5) produced no new files — it only ran the existing test suites and started the dev servers, so it has no entry here.

## Step 1 — Spec Step

### [SRS.md](SRS.md)

1. **What is it?** The Software Requirements Specification — the project's single source of truth for *what* the system does and *why* (existing document, not created by this US).
2. **Why was it created?** Not created — modified. §7.1 System Security already had empty `SS-US-01`/`SS-US-02` headers; this US filled in the missing story statement and added the spec link.
3. **When is it used?** Read before writing/reviewing any user story or acceptance criteria (per CLAUDE.md's trigger table), and whenever someone needs to know *what* a feature is supposed to do.
4. **How does it work?** Two edits: added `> Spec: [specs/001-system-security/spec.md](...)` once under the `### 7.1 System Security (SS)` header, and added the **As a/an... I want to... so that...** story statement under `#### 7.1.1 SS-US-01`. No acceptance criteria live here — those belong only in `spec.md`, per constitution.md's User Story Conventions.

### [specs/001-system-security/spec.md](specs/001-system-security/spec.md)

1. **What is it?** The spec-kit feature specification for the System Security feature — user scenarios, functional requirements, success criteria, and assumptions, generated by `/speckit-specify`.
2. **Why was it created?** SS-US-01 was the first User Story for a brand-new Feature (System Security), so no feature folder existed yet; the Spec Step always produces this file for a feature's first US.
3. **When is it used?** Read by the Design Step (`/speckit-plan`) to produce `plan.md`, by the Quality Step to derive test cases, and by anyone reviewing *why* an acceptance criterion exists.
4. **How does it work?** Structured Markdown following `.specify/templates/spec-template.md`: one User Story (P1) with 4 Acceptance Criteria (`AC-01`..`AC-04`) and 3 Edge Cases (`EC-01`..`EC-03`), 6 Functional Requirements (`FR-001`..`FR-006`), 3 Success Criteria (`SC-001`..`SC-003`), and an Assumptions section. Each `AC-NN`/`EC-NN` has a stable ID + short name so later documents (`test_cases.md`) can reference them unambiguously.

### [specs/001-system-security/checklists/requirements.md](specs/001-system-security/checklists/requirements.md)

1. **What is it?** A spec-quality checklist — content quality, requirement completeness, and feature-readiness checks — generated automatically by `/speckit-specify` right after writing `spec.md`.
2. **Why was it created?** speckit's built-in quality gate: before a spec is considered ready for `/speckit-plan`, every item must be validated (no vague requirements, no unresolved `[NEEDS CLARIFICATION]` markers, measurable success criteria, etc.).
3. **When is it used?** Once, immediately after `spec.md` is drafted — checked by `/speckit-implement`'s pre-implementation gate too (it verifies checklists are complete before letting implementation proceed).
4. **How does it work?** A Markdown checklist with `- [ ]`/`- [x]` items; all 16 items were validated and checked off in one pass since `spec.md` had no ambiguities needing `[NEEDS CLARIFICATION]` markers.

### [.specify/feature.json](.specify/feature.json)

1. **What is it?** A one-line pointer file speckit uses internally: `{"feature_directory": "specs/001-system-security"}`.
2. **Why was it created?** So downstream speckit commands (`/speckit-plan`, `/speckit-tasks`, `/speckit-analyze`, `/speckit-implement`) can find the active feature's directory without depending on git branch-name conventions.
3. **When is it used?** Read by every subsequent speckit slash command in this session — it's how `/speckit-plan` knew to write `plan.md` into `specs/001-system-security/` without being told again.
4. **How does it work?** Plain JSON with a single key; overwritten if a different feature is ever made active.

### [.specify/templates/spec-template.md](.specify/templates/spec-template.md)

1. **What is it?** The template `/speckit-specify` copies from to start every new `spec.md` — not specific to SS-US-01, but modified while writing SS-US-01's spec.
2. **Why was it modified?** Mid-conversation, the naming convention for scenarios was changed: "Acceptance Scenarios" → "Acceptance Criteria", and each item was given a stable `AC-NN`/`EC-NN` ID + short name (numbered sequentially across the whole spec, not reset per story) so `test_cases.md` can cite one unambiguous ID regardless of which user story it belongs to.
3. **When is it used?** Every future `/speckit-specify` run for any new feature — this is a durable, project-wide convention change, not a one-off edit.
4. **How does it work?** It's a Markdown skeleton with bracketed placeholders (`[Brief Title]`, `[AC-01: Short name]`, etc.) that `/speckit-specify` fills in with real content; the ID convention is documented inline as an HTML comment so future runs of the command follow it automatically.

### [specs/001-system-security/plan.md](specs/001-system-security/plan.md)

1. **What is it?** The implementation plan generated by `/speckit-plan` — Technical Context, a Constitution Check, project structure, and Complexity Tracking.
2. **Why was it created?** Every US needs an architecture decision recorded before code is written; here the key decision was **not** to build a new service layer, since login is a stock `djangorestframework-simplejwt` view that already exists.

### [specs/001-system-security/research.md](specs/001-system-security/research.md)

3. **When is it used?** Read alongside `plan.md` during the Design and Implementation Steps; useful context for `/speckit-analyze`'s consistency checks.
4. **How does it work?** A Decision/Rationale/Alternatives-considered format per topic, plus an "Open items carried to implementation" section that was updated to "resolved" once T014/T015 closed those gaps.

### [specs/001-system-security/data-model.md](specs/001-system-security/data-model.md)

1. **What is it?** Phase 1 output of `/speckit-plan` — documents the entities this US touches.
2. **Why was it created?** To make explicit that no schema change was needed — SS-US-01 only *reads* the existing `User.email`/`password`/`is_active` fields.
3. **When is it used?** Read whenever someone needs to know which fields matter for login, or (as later added) why the backend tests use `is_staff`/`is_superuser` to simulate a "dual-role" account.
4. **How does it work?** A simple field table plus a note (added after the pre-implementation `/speckit-analyze` flagged it as a documentation gap) explaining that `is_staff`/`is_superuser` are a test-only stand-in for a `Role` entity that doesn't exist yet.

### [specs/001-system-security/contracts/auth-login.md](specs/001-system-security/contracts/auth-login.md)

1. **What is it?** Phase 1 output of `/speckit-plan` — the API contract for `POST /api/v1/auth/login/` (and its paired `/auth/refresh/`).

3. **When is it used?** Read during implementation to confirm exact response fields (`access`/`refresh`) and error status codes (400/401).
4. **How does it work?** A Markdown contract mapping each field/status back to the specific AC/EC it satisfies (e.g. the 401 case is mapped to both AC-02 and AC-03, since they share one generic error body).

### [specs/001-system-security/quickstart.md](specs/001-system-security/quickstart.md)

1. **What is it?** Phase 1 output of `/speckit-plan` — a runnable validation guide (curl commands, browser steps) proving the feature works end-to-end.
2. **Why was it created?** So a human (or the Deployment/Verification Step) has copy-pasteable commands to validate each AC/EC without reading the whole spec.
3. **When is it used?** During the Implementation Step's manual check (T018) and again conceptually during Deployment/Verification.
4. **How does it work?** One `curl` snippet per AC/EC (e.g. wrong password, deactivated account) plus a "Frontend" section describing the manual browser steps once `frontend/src/app/login/page.tsx` exists.

## Step 3 — Quality Step

### [tests/001-system-security/test_cases.md](tests/001-system-security/test_cases.md)

1. **What is it?** The test case catalogue for SS-US-01 — 9 test cases (`TC-01`..`TC-09`), each classified `[API]`/`[UI]`/`[BOTH]`, with a coverage matrix.
2. **Why was it created?** Constitution.md's DOD-05 requires test coverage for happy paths, error cases, and edge cases before a US is Done; this file is the human-readable plan for that coverage, written before any test code.
3. **When is it used?** Read by the Implementation Step to know exactly which backend `APITestCase`s to write, and by the Verification Step to build the pass/fail results table.
4. **How does it work?** Each `TC-NN` cites the spec.md `AC-NN`/`EC-NN` it verifies, its `Type` (`integration` or `e2e`), and a Given/When/Then. A coverage matrix at the bottom proves every `[BOTH]` item has both an integration and an e2e test case — an empty e2e column there would be a defect.

### [tests/001-system-security/test_ss.spec.ts](tests/001-system-security/test_ss.spec.ts)

1. **What is it?** The Playwright end-to-end test automation for the 3 e2e-typed test cases (TC-02, TC-04, TC-08).
2. **Why was it created?** So the UI-facing behavior (redirect on success, exact inline error text) is automatically checked in a real browser, not just asserted by hand.
3. **When is it used?** Run by the Implementation Step (to verify the login page as it's built), the Deployment Step (regression check), and the Verification Step (final sign-off) — via `npx playwright test tests/001-system-security/test_ss.spec.ts`.
4. **How does it work?** Seeds a test user directly via `POST /api/v1/users/` (never a DB shortcut), then drives a real Chromium browser against `#login-email`/`#login-password`/`#btn-submit-login`/`#message-error` — the exact element IDs the Implementation Step was contractually required to use. It was this file, run for real against live dev servers, that caught a genuine bug: the login page's API URL was missing its `/api/v1` prefix.

### [aif-sdlc.md](aif-sdlc.md)

1. **What is it?** The AIF-SDLC process document — the 6-step prompt templates this entire workflow follows (existing document).
2. **Why was it modified?** Multiple times, each time a workflow gap surfaced while actually running the process on SS-US-01: (a) added an explicit `develop`-as-parent-branch rule to every step's `--- Git ---` section, since Design Step had accidentally branched off the Spec Step branch instead of `develop`; (b) changed the Quality/Implementation/Verification prompts to put test artifacts under a new `tests/[feature-id]-[slug]/` tree instead of inside `specs/`; (c) fixed the Verification Prompt's Playwright-report path to drop an unnecessary `reports/` wrapper folder; (d) added a `test-results/` cleanup step so Playwright's disposable run artifacts don't linger after every Verification run.
3. **When is it used?** Read at the start of every future AIF-SDLC step, for every future US — this file *is* the process, so its accuracy matters for SS-US-02 (Logout) and every subsequent story.
4. **How does it work?** Each fix was applied directly to the relevant prompt template's `--- Git ---` or numbered-step text, so the next time someone (or Claude) follows the prompt verbatim, they get the corrected behavior automatically rather than needing to remember a past correction.

### [CLAUDE.md](CLAUDE.md)

1. **What is it?** The project instructions file auto-loaded into every Claude Code session (existing document).
2. **Why was it modified?** Its Project Structure section and Key Conventions previously said "no `specs/` or E2E test folder exists yet" — no longer true once this US created both; updated to describe the new `specs/`/`tests/` split and that a Playwright runner now exists.
3. **When is it used?** Every session, automatically, before any task — it's the first thing establishing project context.
4. **How does it work?** A repo-layout tree plus short bullet points; kept intentionally brief since the point is fast orientation, not exhaustive documentation.

## Step 4 — Implementation Step

### [specs/001-system-security/tasks.md](specs/001-system-security/tasks.md)

1. **What is it?** The dependency-ordered task breakdown generated by `/speckit-tasks` — 18 tasks (`T001`..`T018`) across Setup/Foundational/User-Story/Polish phases.
2. **Why was it created?** To turn `spec.md`+`plan.md` into an executable checklist before writing any code, and to leave a durable record of what was actually done (each task was checked off `[x]` as completed, with notes on what was discovered along the way — e.g. T017/T018's notes about the Playwright runner and the bug it caught).
3. **When is it used?** Read once during the Implementation Step to drive the work; read afterward by anyone auditing what was built and why.
4. **How does it work?** Each task cites its file path and dependency on other tasks (e.g. T012 depends on T011); a "Parallel Opportunities" section marks which tasks could run concurrently. It's the single most detailed record of the Implementation Step's actual execution.

### [backend/users/tests.py](backend/users/tests.py)

1. **What is it?** The Django `APITestCase` suite for login — 6 tests (`test_tc01`..`test_tc09`), replacing an empty stub.
2. **Why was it created?** Constitution.md's DOD-05 and "Integration Testing Over Mocking" principle require real API tests against a real (throwaway) test database — no mocking of models/querysets.
3. **When is it used?** Run via `python manage.py test users` (or `python manage.py test` for the full suite) — during Implementation (T008), Deployment (regression check), and Verification (re-confirmed fresh).
4. **How does it work?** Each test registers a real user via the actual registration endpoint (never an ORM shortcut that bypasses password hashing), then exercises the login endpoint and asserts the exact status code and response shape — e.g. `test_tc05` deactivates an account mid-test and confirms it gets the *same* generic 401 body as a wrong password, proving AC-02 and AC-03 are indistinguishable to the caller.

### [frontend/src/app/login/page.tsx](frontend/src/app/login/page.tsx)

1. **What is it?** The actual Login page — a Next.js/React client component at the `/login` route.
2. **Why was it created?** It didn't exist at all before this US; SS-US-01 needs a real UI, not just a backend endpoint.
3. **When is it used?** Every time a User opens `http://<host>:3000/login` — it's the literal feature being delivered.
4. **How does it work?** A `"use client"` component with `useState` for `email`/`password`/`error`/`loading`. On submit: if either field is empty, shows `"Email and password are required."` without calling the API (EC-01); otherwise `fetch`es `POST ${apiOrigin}/api/v1/auth/login/` (native fetch, no HTTP client library, per constitution FE-08); on failure shows `"Invalid email or password."` (AC-02/AC-03); on success stores the `access`/`refresh` tokens in `localStorage` and redirects via `useRouter().push('/')` (AC-01). The submit button disables and shows "Logging in..." while the request is in flight (FE-06).

### [package.json](tests/package.json) (tests/)

1. **What is it?** A Node.js manifest for the `tests/` tree — the repo previously had none (only `frontend/package.json`). Originally created at the repo root, later moved into `tests/` so all Playwright tooling is self-contained alongside the spec files it runs.
2. **Why was it created?** To hold `@playwright/test` as a devDependency for the `tests/` tree, which lives as a sibling to `frontend/`, not inside it.
3. **When is it used?** Whenever `npx playwright test` is run from `tests/` (Quality/Implementation/Deployment/Verification Steps).
4. **How does it work?** Auto-generated by `npm init -y` then `npm install -D @playwright/test`; its only real purpose is declaring that one devDependency (plus a `test` script that runs `playwright test`).

### [package-lock.json](tests/package-lock.json) (tests/)

1. **What is it?** The exact dependency-version lockfile paired with `tests/package.json`.
2. **Why was it created?** Automatically, by `npm install` — ensures the same `@playwright/test` version installs deterministically on any other machine (e.g. the actual home-LAN host).
3. **When is it used?** Read by `npm install`/`npm ci`, never edited by hand.
4. **How does it work?** Standard npm lockfile format; not meant to be human-read, just committed so installs are reproducible.

### [playwright.config.ts](tests/playwright.config.ts) (tests/)

1. **What is it?** The Playwright test-runner configuration.
2. **Why was it created?** Without it, `npx playwright test` doesn't know what `--project=chromium` should map to.
3. **When is it used?** Loaded implicitly every time `npx playwright test` runs from `tests/`.
4. **How does it work?** Sets `testDir: "."` (its own directory, i.e. `tests/`), `testMatch: "**/*.spec.ts"`, a `chromium` project using `devices["Desktop Chrome"]`, and a `baseURL` that defaults to `http://localhost:3000` but can be overridden via the `BASE_URL` env var (matching aif-sdlc.md's Verification Prompt convention).

### [.gitignore](.gitignore) (repo root)

1. **What is it?** The repo-wide ignore rules (existing file, previously Python-only).
2. **Why was it modified?** The new root `node_modules/`, Playwright's `test-results/`/`playwright-report/`/`blob-report/` output directories, and ad hoc `.dev-server.log` files (used to capture dev-server output during manual verification) all needed to be excluded from `git status`/commits.
3. **When is it used?** Every `git status`/`git add` — silently, in the background.
4. **How does it work?** A new "Node.js" section was added at the top of the file listing the specific new patterns, without touching the existing Python-focused rules below it.
